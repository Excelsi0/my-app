# Проверки, документация и поставка

## Дисциплина изменений

- Делай минимальное связное изменение и сохраняй несвязанное поведение.
- Не редактируй `.next`, `next-env.d.ts`, `*.tsbuildinfo` и другие generated artifacts.
- Не коммить `.env*`, кроме безопасного шаблона `.env.example`.
- Обновляй `README.md` и `.env.example`, если меняются запуск, команды, обязательные переменные или развёртывание.
- При изменении build/runtime сохраняй рабочий production-путь в `Dockerfile`.
- Не создавай новый package-manager lock-файл; проект использует `bun.lock`.

## Автоматические проверки

Для изменения кода обычный минимум:

```bash
bun run lint
bun run build
```

В проекте пока нет test script и test framework. Не сообщай, что тесты прошли, если были выполнены только lint и build. Не добавляй test framework ради маленького изменения без запроса пользователя или явной инженерной необходимости.

## Проверка по типу задачи

- UI: запусти приложение, проверь затронутые состояния в браузере на mobile и desktop, затем проверь console и failed network requests.
- API: проверь как минимум ответ при отсутствии конфигурации; с доступными ключами проверь успешный и upstream-failure сценарии.
- Финансовая логика: проверь валидные и невалидные записи обоих источников, неизвестные валюты и округление.
- Документация или rules-only: проверь ссылки, пути, команды и отсутствие противоречий; lint/build не обязательны, если исполняемый код и конфигурация не менялись.
- Зависимости и конфиг: выполни чистую установку при необходимости, lint и production build.

Demo-режим должен работать без credentials. Live-режим проверяй только при наличии настоящих ключей. В итоговом сообщении перечисли реально выполненные проверки и явно укажи, что не удалось проверить.
